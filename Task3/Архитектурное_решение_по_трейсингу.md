# Архитектурное решение по трейсингу

## 1. Мотивация

### Проблема: «Распределённый монолит» без видимости

Архитектура «Александрита» состоит из нескольких связанных сервисов: Shop API → MES API → CRM API, связанных через HTTP и RabbitMQ. Когда клиент получает ошибку или ждёт ответа слишком долго, команда не может быстро локализовать проблему:

- Долго отвечает база данных?
- MES API ждёт ответа от внешнего сервиса?
- Запрос «застрял» в очереди RabbitMQ?
- Проблема в сети между сервисами?

**Текущая реальность:** Логи разрознены по разным системам. Метрики показывают *наличие* проблемы (latency вырос), но не *причину* для конкретного запроса. Чтобы понять, что случилось с заказом #12345, инженер тратит часы на ручной поиск по логам трёх систем.

### Цели внедрения трейсинга

1. **Визуализация потока заказа:** Видеть полную цепочку прохождения запроса через все сервисы на одном экране.
2. **Root Cause Analysis:** Быстро находить компонент, вызвавший задержку или ошибку.
3. **Оптимизация latency:** Находить самые медленные участки (spans) в цепочке вызовов.
4. **Корреляция с логами:** Связать трейс с детальными логами по `trace_id`.

### Влияние на метрики (технические и бизнес)

| Метрика | Тип | Текущее состояние | Ожидаемое улучшение |
|---------|-----|-------------------|---------------------|
| **MTTR (Mean Time To Recovery)** | Техническая | Часы (ручной поиск по логам) | Минуты (визуализация в Jaeger) |
| **Время диагностики инцидента** | Техническая | 2-4 часа | 15-30 минут |
| **% инцидентов с найденной root cause** | Техническая | ~50% (часто «не воспроизводится») | >90% |
| **Время ожидания клиента при эскалации** | Бизнес | Дни (пока разберёмся) | Часы |
| **Потерянные B2B-контракты из-за «невидимых» проблем** | Бизнес | Несколько в квартал | Стремится к нулю |

## 2. Анализ системы: точки отказа и покрытие трейсингом

### Критические точки, где заказ может «сломаться» или зависнуть

На основе C4-диаграммы и описания системы выделены следующие точки риска:

| # | Точка | Тип проблемы | Почему критично |
|---|-------|--------------|-----------------|
| 1 | **Shop API → MES API** (расчёт стоимости) | Timeout, 5xx | Клиент не получает цену, заказ не создаётся |
| 2 | **MES API → MES DB** (тяжёлые запросы) | Slow query, deadlock | Дашборд операторов тормозит |
| 3 | **MES API → RabbitMQ** (публикация статуса) | Connection failure, queue full | Сообщение теряется, CRM не знает о заказе |
| 4 | **RabbitMQ → CRM API** (потребление) | Consumer crash, no ACK | Сообщение уходит в DLX или теряется |
| 5 | **CRM API → Shop DB** (Shared DB антипаттерн) | Lock contention, schema mismatch | CRM и Shop блокируют друг друга |
| 6 | **Shop API → S3** (загрузка 3D-модели) | Network timeout, S3 unavailable | Клиент не может загрузить файл |

### Системы, которые необходимо покрыть трейсингом

```

│                    ОБЯЗАТЕЛЬНОЕ ПОКРЫТИЕ                        │
├─────────────────────────────────────────────────────────────────┤
│  ✅ Shop API (Java/Spring Boot)                                 │
│  ✅ MES API (C#)                                                │
│  ✅ CRM API (Java/Spring Boot)                                  │
│  ✅ RabbitMQ (producer & consumer spans)                        │

│  ⚠️  S3 operations — для диагностики загрузки файлов           │
└─────────────────────────────────────────────────────────────────┘
```

## 3. Данные, которые должны попадать в трейсинг

### Обязательные атрибуты спанов (Span Attributes)

| Категория | Атрибут | Пример | Зачем |
|-----------|---------|--------|-------|
| **Идентификация** | `service.name` | `shop-api` | Группировка спанов по сервису |
| | `service.version` | `1.2.3` | Понять, на какой версии проблема |
| | `deployment.environment` | `prod` | Различать окружения |
| **HTTP** | `http.method` | `POST` | Тип операции |
| | `http.url` | `/api/orders` | Эндпоинт (без query params!) |
| | `http.status_code` | `500` | Результат |
| | `http.request_content_length` | `1024` | Размер запроса |
| **Бизнес-контекст** | `order.id` | `12345` | Связь с бизнес-сущностью |
| | `order.status` | `SUBMITTED` | Текущий статус |
| | `customer.id` | `cust_789` | ID клиента (не PII!) |
| **Database** | `db.system` | `postgresql` | Тип БД |
| | `db.name` | `mes_db` | Имя базы |
| | `db.statement` | `SELECT...` | Запрос (sanitized!) |
| **Messaging** | `messaging.system` | `rabbitmq` | Тип очереди |
| | `messaging.destination` | `orders.status` | Имя очереди/топика |
| | `messaging.message_id` | `msg_123` | ID сообщения |

### События внутри спанов (Span Events)

| Событие | Когда добавлять | Пример данных |
|---------|-----------------|---------------|
| `order.status_changed` | При смене статуса заказа | `old_status`, `new_status` |
| `calculation.started` | Начало расчёта стоимости | `model_complexity` |
| `calculation.completed` | Завершение расчёта | `duration_ms`, `price` |
| `exception` | При ошибке | `exception.type`, `exception.message` |

## 4. Предлагаемое решение

### Технологический стек

| Компонент | Технология | Обоснование |
|-----------|------------|-------------|
| **Instrumentation** | OpenTelemetry SDK | Vendor-neutral стандарт, поддержка Java/C#/JS |
| **Protocol** | OTLP (gRPC) | Эффективный бинарный протокол |
| **Collector** | OpenTelemetry Collector | Буферизация, батчинг, routing |
| **Backend** | Jaeger | Open-source, хорошая визуализация, интеграция с K8s |

## 5. Стратегия сэмплирования (Sampling)

### MVP / Development

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| Стратегия | `AlwaysOn` (100%) | На этапе отладки нужно видеть каждый запрос |
| Retention | 7 дней | Достаточно для разработки |

### Production

| Параметр | Значение | Обоснование |
|----------|----------|-------------|
| Стратегия | `ParentBased` + `TraceIdRatioBased` | Наследуем решение родителя, иначе — probabilistic |
| Ratio | 0.1 (10%) | Баланс между visibility и стоимостью хранения |
| Error sampling | 100% для `span.status = ERROR` | Ошибки всегда сохраняем |
| Retention | 30 дней | Для post-mortem анализа |

**Расчёт storage:**
- ~1000 RPS × 10% sampling × 5 KB/trace × 86400 sec = ~43 GB/день
- 30 дней retention = ~1.3 TB (приемлемо для Elasticsearch)

## 6. Компромиссы

### Когда трейсинг не принесёт пользы или будет дорогим

| Сценарий | Проблема | Рекомендация |
|----------|----------|--------------|
| **Очень высокая нагрузка (>10K RPS)** | Storage и сеть не справятся с 100% трейсов | Использовать агрессивный sampling (1-5%) |
| **Legacy-код без возможности модификации** | Нельзя добавить инструментацию | Использовать service mesh (Istio) для sidecar-трейсинга |
| **Проприетарные системы (например, купленный MES)** | Vendor не предоставляет hooks | Трейсить только «снаружи» (входящие/исходящие вызовы) |
| **Асинхронные batch-процессы** | Нет явного «запроса» для привязки трейса | Создавать synthetic span при старте batch job |
| **Фронтенд-only проблемы** | JS-ошибки в браузере | Browser tracing сложнее, лучше использовать Sentry/LogRocket |

### Ограничения текущего решения

1. **RabbitMQ context propagation** требует явной передачи headers в message properties — нужна доработка продюсеров и консьюмеров.
2. **Shared DB (CRM → Shop DB)** — трейсинг покажет, что CRM делает запрос, но не свяжет его с Shop API (нет общего trace context).
3. **Tail-based sampling** (сохранять только проблемные трейсы) требует буферизации и более сложной инфраструктуры — отложено на v2.

## 7. Аспекты безопасности

### Защита чувствительных данных

| Угроза | Мера защиты |
|--------|-------------|
| PII в span attributes | **Whitelist-подход:** логируем только разрешённые поля (IDs, статусы). Запрещены: email, phone, password, credit_card, address |
| SQL-запросы с данными | **Sanitization:** `db.statement` содержит только структуру запроса, параметры заменяются на `?` |
| Тела запросов/ответов | **Запрет:** не логируем body целиком, только `content_length` |
| Токены авторизации | **Исключение:** заголовки `Authorization`, `Cookie` не попадают в спаны |

### Контроль доступа

| Компонент | Мера защиты |
|-----------|-------------|
| Jaeger UI | Доступ только через VPN или внутреннюю сеть. На MVP — `kubectl port-forward`. |
| OTEL Collector | Принимает трафик только из внутренней сети (не exposed наружу) |
| Elasticsearch | Закрыт за firewall, доступ только от Jaeger |

### Аудит доступа

- Включить audit log в Jaeger/Elasticsearch для отслеживания, кто просматривал трейсы.
- Роли: `viewer` (просмотр), `admin` (настройка sampling, удаление данных).

## 8. Интеграция с логированием

### Корреляция Traces ↔ Logs

Для связи трейсов с логами добавляем `trace_id` и `span_id` в каждую лог-запись:

**Java (Spring Boot + Logback):**
```xml
<pattern>%d{ISO8601} [%thread] %-5level %logger{36} [trace_id=%X{trace_id} span_id=%X{span_id}] - %msg%n</pattern>
```

**C# (Serilog):**
```csharp
Log.Logger = new LoggerConfiguration()
    .Enrich.WithProperty("trace_id", Activity.Current?.TraceId.ToString())
    .Enrich.WithProperty("span_id", Activity.Current?.SpanId.ToString())
    .CreateLogger();
```

### Workflow диагностики

1. В Jaeger находим медленный/ошибочный трейс.
2. Копируем `trace_id`.
3. В Kibana/Elasticsearch ищем: `trace_id: "abc123"`.
4. Видим детальные логи всех сервисов для этого запроса.

## 9. Мониторинг и алертинг на основе трейсинга (Дополнительное задание)

### Автоматический мониторинг прохождения заказа

На основе данных трейсинга можно построить автоматический мониторинг бизнес-процесса:

**Метрики, извлекаемые из трейсов:**

| Метрика | Источник | Алерт |
|---------|----------|-------|
| Время полного цикла заказа | Root span duration | > 5 минут — Warning, > 30 минут — Critical |
| % ошибок на этапе расчёта цены | MES API span status | > 5% — Critical |
| Время ожидания в очереди RabbitMQ | Разница между publish и consume spans | > 60 секунд — Warning |
| Количество «застрявших» заказов | Трейсы без завершающего span > 24h | > 0 — Critical |

### Пример алертов (Prometheus rules)

```yaml
groups:
  - name: tracing-alerts
    rules:
      - alert: HighOrderProcessingTime
        expr: histogram_quantile(0.95, rate(order_processing_duration_seconds_bucket[5m])) > 300
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Order processing time p95 > 5 minutes"
          
      - alert: MESCalculationErrors
        expr: rate(mes_calculation_errors_total[5m]) / rate(mes_calculation_total[5m]) > 0.05
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "MES price calculation error rate > 5%"
          
      - alert: RabbitMQQueueDelay
        expr: rabbitmq_message_queue_time_seconds > 60
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "Messages waiting in queue > 60 seconds"
```

## Резюме

Внедрение распределённого трейсинга на базе OpenTelemetry + Jaeger позволит:

1. **Видеть полный путь заказа** через Shop → MES → CRM на одном экране.
2. **Сократить время диагностики** инцидентов с часов до минут.
3. **Находить bottleneck'и** в цепочке вызовов для оптимизации latency.
4. **Связать трейсы с логами** по `trace_id` для глубокого анализа.
5. **Автоматически алертить** о проблемах в бизнес-процессе на основе данных трейсинга.

Решение построено на открытых стандартах (W3C Trace Context, OTLP), что обеспечивает vendor-independence и возможность миграции на другие бэкенды в будущем.
