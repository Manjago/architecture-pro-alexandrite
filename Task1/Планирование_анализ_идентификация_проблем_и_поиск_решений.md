# Планирование: анализ, идентификация проблем и поиск решений

## Контекст

Компания «Александрит» переживает период активного роста: нагрузка увеличивается на ~100 заказов ежемесячно, открыт публичный API для B2B-партнёров. При этом инфраструктура и архитектура остались на уровне стартапа: один инстанс на каждый сервис, ручные деплои, отсутствие observability. Результат — потеря крупных контрактов и рост недовольства клиентов.

---

## 1. Идентифицированные проблемы

### 1.1. Отсутствие наблюдаемости (Observability)

**Симптом:** О проблемах команда узнаёт от клиентов — звонки, жалобы, потерянные контракты. Яндекс Метрика покрывает только фронтенд магазина и бесполезна для API-интеграций.

**Причина:** Нет централизованного мониторинга, трейсинга и логирования. Команда работает «вслепую» — невозможно понять, где именно «застревает» заказ: в очереди RabbitMQ, в расчёте MES или в интеграции с CRM.

**Влияние на бизнес:** Время реакции на инциденты измеряется днями. Репутационные потери, отток B2B-клиентов.

### 1.2. Деградация производительности MES

**Симптом:** Дашборд с заказами загружается неприемлемо долго. Команда уже внедрила фильтры по статусам и пагинацию — не помогло.

**Вероятные причины:**
- Неоптимальные SQL-запросы (например, `SELECT *` с тяжёлыми JOIN-ами вместо проекций).
- Отсутствие индексов на часто фильтруемых полях (статус, дата создания).
- Пагинация может быть реализована на фронтенде, но бэкенд всё равно достаёт все записи.
- Единственный инстанс БД обслуживает и чтение дашборда, и запись статусов — взаимные блокировки.

**Влияние на бизнес:** Операторы теряют время, падает их производительность и мотивация (система вознаграждения привязана к скорости взятия заказов).

### 1.3. Долгий расчёт стоимости (2–30 минут)

**Симптом:** Клиенты ждут результат расчёта слишком долго. При сложных 3D-моделях время достигает 30 минут.

**Причина:** Расчёт стоимости — CPU-bound задача (анализ полигонов 3D-модели). Если расчёт выполняется синхронно в рамках HTTP-запроса, это критическая проблема: поток заблокирован, при таймауте клиент остаётся без ответа.

**Риски:**
- Если нет асинхронной обработки — любой всплеск запросов «кладёт» MES API.
- Нет статуса «Расчёт в процессе» — клиент не понимает, что происходит.

### 1.4. Потеря сообщений в RabbitMQ

**Симптом:** API-пользователи ежедневно сообщают, что не получили свои заказы. Заказы «теряются» между MES и CRM.

**Вероятные причины:**
- Отсутствует Dead Letter Exchange (DLX) — сообщения, которые не удалось обработать, просто пропадают.
- Нет подтверждений (ACK) или используется auto-ack — сообщение считается обработанным до фактической обработки.
- Очередь переполняется при пиковых нагрузках (нет ограничений, нет бэкпрессера).
- Consumer падает без корректной обработки — сообщение теряется.

**Влияние на бизнес:** Прямые финансовые потери, утрата доверия B2B-партнёров.

### 1.5. Антипаттерн Shared Database

**Симптом:** CRM API напрямую обращается к Shop DB (видно на C4-диаграмме).

**Проблемы:**
- Жёсткая связанность (tight coupling): изменение схемы в Shop DB может сломать CRM.
- Конкуренция за ресурсы: запросы CRM могут блокировать или замедлять Shop, и наоборот.
- Нарушение принципа единственной ответственности: две команды должны координировать изменения в одной БД.

**Риск:** При росте нагрузки эта связь станет узким местом. Рефакторинг будет болезненным.

### 1.6. Отсутствие горизонтального масштабирования (SPOF)

**Симптом:** Каждое приложение и каждая БД имеют по одному инстансу.

**Проблемы:**
- Single Point of Failure: падение любого EC2 или managed-сервиса = полная остановка соответствующей части бизнеса.
- Невозможно справиться с пиковыми нагрузками.
- Maintenance window требует даунтайма.

### 1.7. Незрелый CI/CD и релизный процесс

**Симптом:** Деплой в release и prod — ручной. Задержки релизов выросли с 1 месяца до неопределённого срока.

**Причина:** QA прогоняет E2E-тесты вручную. При обнаружении high/highest багов релиз блокируется. Чем больше кода — тем больше багов — тем дольше релизы.

**Влияние:** Команда боится деплоить, фиксы доходят до прода медленно, технический долг накапливается.

## 2. Инициативы для устранения проблем

### Инициатива 1: Внедрение Observability-стека (Must Have)

**Описание:** Развернуть систему мониторинга (Prometheus + Grafana или Yandex Monitoring), централизованное логирование (ELK/OpenSearch), распределённый трейсинг (Jaeger/Zipkin).

**Ожидаемый результат:**
- Команда видит метрики в реальном времени: RPS, latency, error rate.
- Можно отследить путь заказа через все системы (Shop → MES → CRM).
- Алерты при аномалиях, а не звонки от клиентов.

**Приоритет:** Критический. Без observability все остальные улучшения — стрельба вслепую.

### Инициатива 2: Кеширование списков заказов в MES (High Priority)

**Описание:** Внедрить серверное кеширование (Redis) для тяжёлых read-операций: списки заказов по статусам, дашборды. Использовать паттерн Cache-Aside с TTL и инвалидацией при изменении статуса.

**Ожидаемый результат:**
- Время загрузки дашборда сокращается с секунд до миллисекунд.
- Снижается нагрузка на MES DB.

**Дополнительно:** Провести аудит SQL-запросов, добавить индексы, убедиться что пагинация работает на уровне БД (OFFSET/LIMIT или keyset pagination).

### Инициатива 3: Асинхронный расчёт стоимости + статус «Calculating»

**Описание:** Вынести расчёт стоимости в background workers (очередь задач). API сразу возвращает `202 Accepted` с `order_id` и статусом `CALCULATING`. Клиент может polling'ом или через webhook узнать результат.

**Ожидаемый результат:**
- API не блокируется на 2–30 минут.
- Можно масштабировать воркеры независимо от API.
- Прозрачность для клиента: он видит прогресс.

### Инициатива 4: Надёжность RabbitMQ

**Описание:**
- Настроить Dead Letter Exchange (DLX) для сообщений, которые не удалось обработать.
- Перейти на manual acknowledgements.
- Добавить мониторинг глубины очередей и количества DLX-сообщений.
- Реализовать ретраи с экспоненциальным backoff.

**Ожидаемый результат:** Сообщения не теряются. Проблемные сообщения можно проанализировать и переобработать.

### Инициатива 5: Разделение CRM и Shop DB (Medium Priority)

**Описание:** CRM должна получать данные через Shop API, а не напрямую из БД. В перспективе — выделить отдельную реплику для read-операций или внедрить Event-Driven Architecture (CRM подписывается на события заказов через RabbitMQ).

**Ожидаемый результат:**
- Слабая связанность между системами.
- Возможность независимо развивать и масштабировать.

### Инициатива 6: Репликация баз данных

**Описание:** Настроить read-реплики для Shop DB и MES DB. Направить read-трафик (особенно тяжёлые аналитические запросы и дашборды) на реплики.

**Ожидаемый результат:**
- Повышение отказоустойчивости.
- Снижение нагрузки на master.
- Возможность выполнять maintenance без даунтайма.

### Инициатива 7: Автоматизация CI/CD

**Описание:**
- Автоматизировать E2E-тесты (QA-инженер хочет этим заняться — дать ему возможность).
- Внедрить автоматический деплой в release после прохождения тестов.
- Рассмотреть canary-деплои или blue-green для prod.

**Ожидаемый результат:**
- Релизы выходят чаще и предсказуемее.
- Снижается страх деплоя, команда быстрее доставляет фиксы.

### Инициатива 8: Горизонтальное масштабирование API

**Описание:** Запустить минимум 2 инстанса для каждого API за Load Balancer. В перспективе — миграция на Kubernetes для автоскейлинга.

**Ожидаемый результат:**
- Устранение SPOF на уровне приложений.
- Возможность справляться с пиками нагрузки.

## 3. Приоритизация инициатив

| Приоритет | Инициатива | Обоснование |
|-----------|------------|-------------|
| 1 | Observability | Фундамент для всех решений. Без метрик не поймём, помогают ли остальные изменения. |
| 2 | Кеширование MES | Quick win: высокий impact, относительно низкая сложность. Сразу снимает боль операторов. |
| 3 | Надёжность RabbitMQ | Критично для B2B — прямые финансовые потери от потерянных заказов. |
| 4 | Асинхронный расчёт | Важно для UX, но требует изменений в API-контракте и фронтенде. |
| 5 | CI/CD автоматизация | Ускорит доставку всех остальных улучшений. |
| 6 | Репликация БД | Повышает надёжность и производительность, но требует инфраструктурных изменений. |
| 7 | Разделение CRM/Shop | Архитектурный рефакторинг — важно, но не срочно. |
| 8 | Горизонтальное масштабирование | Станет актуально после стабилизации. |

## 4. Целевая архитектура через полгода

Через 6 месяцев система «Александрит» должна выглядеть так:

**Observability:** Полноценный стек мониторинга. Дашборды показывают SLA в реальном времени. Алерты приходят в Slack/Telegram при отклонениях. Трейсинг позволяет за минуты найти, где «застрял» конкретный заказ.

**Производительность:** MES-дашборд загружается за <1 секунду благодаря кешированию и оптимизированным запросам. Расчёт стоимости работает асинхронно, клиенты видят статус в реальном времени.

**Надёжность:** RabbitMQ настроен с DLX, manual ack, мониторингом. Потери сообщений близки к нулю. Базы данных имеют read-реплики.

**CI/CD:** E2E-тесты автоматизированы. Релизы в release-окружение происходят автоматически. Prod-деплой — semi-automated с approval.

**Масштабируемость:** API-сервисы запущены минимум в 2 инстансах за балансировщиком.

## 5. Топ-3 инициативы на ближайшие полгода

Если ресурсы ограничены и можно реализовать только три инициативы:

### 1. Observability (Мониторинг + Логирование + Трейсинг)

**Почему:** Это инвестиция, которая окупается сразу. Сейчас команда работает вслепую — любое улучшение будет требовать недели на диагностику. С observability:
- Проактивно находим проблемы до жалоб клиентов.
- Видим реальные bottleneck'и, а не предполагаем.
- Можем измерить эффект от любых изменений.

### 2. Кеширование MES + оптимизация запросов

**Почему:** Быстрая победа с высоким impact. Операторы — это внутренние пользователи, их продуктивность напрямую влияет на throughput производства. Решение относительно изолированное (только MES), не требует координации между командами.

### 3. Автоматизация CI/CD + надёжность RabbitMQ

**Почему объединяю:** Обе инициативы — про надёжность доставки: одна — кода, другая — данных.

- CI/CD-автоматизация ускорит доставку фиксов. Без неё любое улучшение будет «застревать» в очереди на релиз.
- Надёжность RabbitMQ — критично для B2B, где потеря заказа = потеря контракта.

QA-инженер хочет заняться автоматизацией — это мотивированный ресурс, не нужно нанимать.

## Резюме

Компания «Александрит» находится в типичной ситуации: бизнес вырос быстрее, чем технологическая платформа. Ключевая проблема — отсутствие visibility: мы не знаем, что происходит внутри системы, и реагируем постфактум.

Предложенный план начинается с построения observability-фундамента, затем решает наиболее болезненные проблемы (MES, RabbitMQ) и закладывает основу для масштабирования.

Первые три инициативы (Observability, Кеширование, CI/CD + RabbitMQ) можно реализовать параллельно разными членами команды, что позволит получить ощутимый результат уже через 2–3 месяца.
