# Выбор и настройка мониторинга в системе

## 1. Мотивация

### Текущее состояние

Сейчас единственный инструмент мониторинга в «Александрите» — Яндекс Метрика, подключённая к фронтенду онлайн-магазина. Это создаёт критические слепые зоны:

**Проблема 1: API-трафик невидим**

После открытия публичного API для B2B-партнёров значительная часть бизнеса проходит мимо Яндекс Метрики. B2B-клиенты не загружают веб-страницы с JS-счётчиками — они отправляют HTTP-запросы напрямую в API. Когда партнёр жалуется «ваш API не работает», у нас нет данных для диагностики.

**Проблема 2: Нет видимости бэкенда**

Яндекс Метрика показывает время загрузки страницы глазами браузера. Но она не отвечает на вопрос *почему* страница грузилась 10 секунд:
- База данных выполняла тяжёлый запрос?
- Очередь RabbitMQ переполнена?
- CPU сервера на 100%?
- Сеть между сервисами деградировала?

Без инструментации бэкенда мы гадаем на кофейной гуще.

**Проблема 3: Реактивный режим работы**

Сейчас о проблемах команда узнаёт от клиентов: звонки, жалобы в поддержку, потерянные контракты. Это означает, что:
- Время реакции измеряется часами/днями, а не минутами.
- Репутационный ущерб уже нанесён.
- Мы не можем оценить масштаб проблемы («сколько клиентов затронуто?»).

**Проблема 4: Нет базовых линий (baselines)**

Без исторических метрик невозможно понять, является ли текущее поведение нормальным. «100 RPS — это много или мало?» «Latency 500ms — это деградация или норма?»

### Что даст внедрение мониторинга

| Было | Станет |
|------|--------|
| Узнаём о проблемах от клиентов | Алерт в Slack за 30 секунд до первой жалобы |
| «Где-то тормозит» | «MES API latency p95 = 3.2s, причина: DB connections = 100/100» |
| Нет данных для B2B | Полная видимость всех API-вызовов |
| Ручной анализ при инцидентах | Дашборды в реальном времени |
| Невозможно планировать ёмкость | Тренды нагрузки, прогнозирование |

## 2. Выбор подхода к мониторингу

Для комплексного покрытия системы используем **комбинированный подход** из трёх методологий:

### RED Method — для API-сервисов

Применяется к: **Shop API, CRM API, MES API**

| Сигнал | Что измеряем | Почему важно |
|--------|--------------|--------------|
| **R**ate | Количество запросов в секунду (RPS) | Понимание нагрузки, обнаружение аномалий (спад = отказ, всплеск = DDoS/акция) |
| **E**rrors | Количество ошибок (HTTP 5xx) | Индикатор здоровья приложения |
| **D**uration | Время ответа (Latency) | Главный показатель качества для пользователя |

**Обоснование выбора:** RED — стандарт де-факто для мониторинга HTTP-сервисов. Три метрики дают полную картину состояния API с точки зрения клиента.

### USE Method — для инфраструктуры

Применяется к: **PostgreSQL, RabbitMQ, S3, EC2-инстансы**

| Сигнал | Что измеряем | Почему важно |
|--------|--------------|--------------|
| **U**tilization | % использования ресурса (CPU, Memory, Disk) | Понимание, насколько ресурс загружен |
| **S**aturation | Очередь к ресурсу (DB connections, queue depth) | Предиктор проблем: если очередь растёт — скоро будут отказы |
| **E**rrors | Ошибки ресурса (disk errors, connection failures) | Индикатор деградации инфраструктуры |

**Обоснование выбора:** USE оптимален для ресурсо-ориентированных компонентов. Особенно важен сигнал Saturation — он предсказывает проблемы до их возникновения.

### Business Metrics — для бизнес-процессов

Применяется к: **Заказы, Расчёты, Конверсии**

Технические метрики могут быть «зелёными», но бизнес при этом стоит. Пример: все сервера работают, но заказы не создаются из-за бага в логике. Поэтому добавляем бизнес-метрики как «четвёртый золотой сигнал».

## 3. Выбранные метрики для отслеживания

### Группа А: API-сервисы (RED Method)

*Применяется к Shop API, CRM API, MES API*

#### Rate — Количество запросов

| № | Метрика | Зачем нужна | Ярлыки (Labels) |
|---|---------|-------------|-----------------|
| 3 | RPS for Shop API | Основной трафик B2C и B2B | `endpoint`, `method`, `status_code` |
| 4 | RPS for CRM API | Трафик продавцов | `endpoint`, `method`, `user_id` |
| 5 | RPS for MES API | Трафик операторов + внутренние вызовы | `endpoint`, `method`, `source` |

**Примечание по ярлыкам:**
- `endpoint` — для понимания, какие эндпоинты нагружены (например, `/orders` vs `/catalog`).
- `method` — GET/POST/PUT для различения read/write операций.
- `source` — для MES API важно различать запросы от фронтенда и от внутренних сервисов.

#### Errors — Ошибки

| № | Метрика | Зачем нужна | Ярлыки (Labels) |
|---|---------|-------------|-----------------|
| 28 | HTTP 500 for Shop API | Критические ошибки, влияющие на клиентов | `endpoint`, `error_type` |
| 29 | HTTP 500 for CRM API | Ошибки, блокирующие работу продавцов | `endpoint`, `error_type` |
| 30 | HTTP 500 for MES API | Ошибки производственной системы | `endpoint`, `error_type` |

**Дополнительно отслеживаем:**
- HTTP 4xx (клиентские ошибки) — для обнаружения проблем с валидацией или авторизацией.
- Error Rate (%) = 5xx / total requests — более информативно, чем абсолютное число.

#### Duration — Latency

| № | Метрика | Зачем нужна | Ярлыки (Labels) |
|---|---------|-------------|-----------------|
| 19 | Latency for Shop API | UX клиентов магазина | `endpoint`, `quantile` |
| 20 | Latency for CRM API | Продуктивность продавцов | `endpoint`, `quantile` |
| 21 | Latency for MES API | Критично для операторов (дашборд!) | `endpoint`, `quantile` |

**Важно:** Измеряем **перцентили** (p50, p95, p99), а не среднее значение. Среднее скрывает проблемы: если 99% запросов выполняются за 100ms, а 1% за 10 секунд — среднее покажет ~200ms, что выглядит нормально, но 1% пользователей страдает.

#### Resource Utilization

| № | Метрика | Зачем нужна | Ярлыки (Labels) |
|---|---------|-------------|-----------------|
| 9-11 | CPU % for APIs | Сигнал к масштабированию | `service`, `instance` |
| 12-14 | Memory Utilisation for APIs | Обнаружение memory leaks | `service`, `instance` |

### Группа Б: Инфраструктура (USE Method)

#### RabbitMQ

| № | Метрика | USE-сигнал | Зачем нужна | Ярлыки |
|---|---------|------------|-------------|--------|
| 2 | Messages in flight | **Saturation** | Если растёт — консьюмеры не справляются. Предиктор потери сообщений. | `queue_name` |
| 1 | Dead-letter-exchange messages | **Errors** | Сообщения, которые не удалось обработать. Требуют ручного разбора. | `queue_name`, `reason` |

**Дополнительные метрики RabbitMQ:**
- `rabbitmq_queue_consumers` — количество активных консьюмеров.
- `rabbitmq_queue_memory` — память, занимаемая очередью.

#### PostgreSQL (Shop DB, MES DB)

| № | Метрика | USE-сигнал | Зачем нужна | Ярлыки |
|---|---------|------------|-------------|--------|
| 17-18 | DB Connections | **Saturation** | Упёрлись в лимит (default=100) = сервис встаёт. | `database`, `state` |
| 15-16 | Memory Utilisation for DB | **Utilization** | Нехватка памяти = деградация запросов. | `database` |
| 23-24 | Size of DB instance | **Utilization** | Планирование ёмкости, обнаружение аномального роста. | `database` |

**Дополнительные метрики PostgreSQL:**
- `pg_stat_activity` — активные запросы, блокировки.
- `pg_stat_statements` — топ медленных запросов.
- `pg_replication_lag` — задержка репликации (когда внедрим реплики).

#### S3 Storage

| № | Метрика | USE-сигнал | Зачем нужна | Ярлыки |
|---|---------|------------|-------------|--------|
| 22 | Size of S3 storage | **Utilization** | Контроль затрат, обнаружение аномалий (кто-то заливает терабайтные модели). | `bucket` |

---

### Группа В: Бизнес-метрики

*Эти метрики отсутствуют в исходном списке, но критичны для SRE-подхода.*

| Метрика | Зачем нужна | Ярлыки |
|---------|-------------|--------|
| Количество созданных заказов (за 5 мин) | Если падает в ноль в рабочее время — P0 инцидент, даже если инфраструктура «зелёная» | `source` (web/api), `type` (b2c/b2b) |
| Время расчёта стоимости (MES) | Бизнес-SLA. Клиенты ждут результат. | `complexity` (simple/complex) |
| Конверсия корзины в заказ | Косвенный индикатор проблем в checkout flow | — |
| Количество заказов в статусе > 24ч | «Застрявшие» заказы — проблема бизнеса | `status` |

## 4. Показатели насыщенности и пороговые значения

### Определение порогов (Thresholds)

| Компонент | Метрика | Warning | Critical | Действие при превышении |
|-----------|---------|---------|----------|------------------------|
| **API Services** | Error Rate | > 1% | > 5% | Warning: создать тикет. Critical: алерт в Slack, wake-up call дежурному. |
| **API Services** | Latency p95 | > 1s | > 3s | Warning: расследование. Critical: эскалация, возможен rollback. |
| **API Services** | CPU % | > 70% | > 90% | Warning: запланировать масштабирование. Critical: автоскейлинг (если настроен) или ручное добавление инстансов. |
| **PostgreSQL** | Connections | > 80% лимита | > 95% лимита | Warning: увеличить пул. Critical: срочно увеличить лимит или добавить реплику. |
| **PostgreSQL** | Disk Usage | > 70% | > 85% | Warning: запланировать расширение. Critical: срочное расширение или очистка. |
| **RabbitMQ** | Messages in flight | > 10,000 | > 50,000 | Warning: проверить консьюмеров. Critical: добавить консьюмеров, расследовать причину. |
| **RabbitMQ** | DLX messages | > 0 | > 100 | Warning: разобрать вручную. Critical: остановить продюсеров, расследовать. |

### Процедуры реагирования

**При Warning-алерте:**
1. Создаётся тикет в Jira с приоритетом Medium.
2. Ответственный инженер анализирует в рабочее время.
3. Если не решено за 24 часа — эскалация.

**При Critical-алерте:**
1. Немедленное уведомление в Slack-канал `#incidents`.
2. Если вне рабочего времени — звонок дежурному через PagerDuty/Opsgenie.
3. Создаётся инцидент, начинается война комнатная (war room).
4. После решения — обязательный post-mortem.

## 5. План действий (Roadmap)

### Этап 1: Инфраструктура мониторинга (Неделя 1)

| Задача | Описание | Ответственный |
|--------|----------|---------------|
| Развернуть Prometheus | Использовать Prometheus Operator в Kubernetes или Managed Prometheus (Yandex Monitoring) | DevOps |
| Развернуть Grafana | Для визуализации дашбордов | DevOps |
| Настроить Alertmanager | Интеграция с Slack/Telegram для алертов | DevOps |

### Этап 2: Инструментация приложений (Неделя 2-3)

| Задача | Описание | Ответственный |
|--------|----------|---------------|
| Shop API + CRM API (Java) | Добавить `spring-boot-starter-actuator` + `micrometer-registry-prometheus` | Java-разработчики |
| MES API (C#) | Добавить `prometheus-net` + `/metrics` endpoint | C#-разработчик |
| Настроить ServiceMonitor | Prometheus автоматически обнаруживает сервисы | DevOps |

### Этап 3: Exporters для инфраструктуры (Неделя 2)

| Задача | Описание | Ответственный |
|--------|----------|---------------|
| PostgreSQL Exporter | `postgres_exporter` для Shop DB и MES DB | DevOps |
| RabbitMQ Exporter | Встроенный Prometheus plugin или `rabbitmq_exporter` | DevOps |
| Node Exporter | Метрики EC2-инстансов (CPU, Memory, Disk) | DevOps |

### Этап 4: Дашборды (Неделя 3-4)

| Дашборд | Аудитория | Содержимое |
|---------|-----------|------------|
| «Traffic Lights» | Менеджмент, продакт | Зелёный/жёлтый/красный статус каждой системы. Минимум деталей. |
| «API Overview» | Разработчики, SRE | RPS, Latency, Errors по каждому сервису. Drill-down по эндпоинтам. |
| «Database Health» | DBA, разработчики | Connections, slow queries, replication lag. |
| «RabbitMQ» | Разработчики | Queue depth, DLX, consumer count. |
| «Business Metrics» | Продакт, менеджмент | Заказы, конверсии, «застрявшие» заказы. |

### Этап 5: Алертинг (Неделя 4)

| Алерт | Условие | Канал | Severity |
|-------|---------|-------|----------|
| High Error Rate | Error Rate > 5% за 5 минут | Slack `#incidents` + PagerDuty | Critical |
| High Latency | p95 > 3s за 5 минут | Slack `#incidents` | Critical |
| DB Connections Exhausted | > 95% лимита | Slack `#incidents` + PagerDuty | Critical |
| DLX Messages | > 0 | Slack `#alerts` | Warning |
| Zero Orders | 0 заказов за 15 минут в рабочее время | Slack `#incidents` + PagerDuty | Critical |

## 7. Ожидаемые результаты

| Метрика | До | После |
|---------|-----|-------|
| Время обнаружения инцидента | Часы/дни (от клиентов) | Минуты (алерты) |
| Время диагностики | Часы (логи вручную) | Минуты (дашборды) |
| MTTR (Mean Time To Recovery) | Неизвестно | Измеримо, цель < 1 часа |
| Видимость API-трафика | 0% | 100% |
| Проактивное масштабирование | Невозможно | На основе трендов |

## Резюме

Внедрение мониторинга на базе Prometheus + Grafana с использованием методологий RED (для сервисов) и USE (для инфраструктуры) позволит:

1. **Выйти из слепой зоны** — видеть всё, что происходит в системе, включая API-трафик B2B.
2. **Перейти от реактивного к проактивному режиму** — узнавать о проблемах до клиентов.
3. **Сократить время диагностики** — от часов к минутам благодаря дашбордам и drill-down.
4. **Обосновывать решения данными** — масштабирование, оптимизации, приоритизация задач.

Реализация займёт ~4 недели силами DevOps-инженера с частичным вовлечением разработчиков для инструментации приложений.
